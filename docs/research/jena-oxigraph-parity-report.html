Executive decision

Use Jena as a reference capability portfolio, not a Java API to clone. Oxigraph already has a credible database core; the programme should add missing outcomes through explicit, testable extension contracts.

No single parity percentage. SHACL conformance, rule inference, operational security, and query-builder ergonomics carry different value and risk. Progress is measured per domain with supported profiles and executable gates.

Immediate portfolio move

Build the conformance/evidence harness and semantic extension seams first; then deliver SHACL Core and RDFS inference in constrained profiles. Continue GeoSPARQL as small, standards-backed increments.

Implemented now: geof:boundary

Selected because GeoSPARQL 1.1 requires it, Jena implements it, the local Oxigraph inventory marked it missing, and it fits the existing spargeo seam.

  • Registered as GeoSPARQL extension function 44
  • Polygon shells and holes return lineal boundaries
  • Line collections use MOD-2 endpoint semantics
  • Point boundaries are empty geometry collections
  • WKT and GeoJSON output datatypes are preserved
  • GeometryCollection error behavior follows Jena/JTS
  • Scope remains honestly limited to current CRS84 parsing

Evidence rules

  1. Official releases establish current versions.
  2. Official docs establish supported capability outcomes.
  3. Observed source establishes concrete module and behavior evidence.
  4. Normative standards establish conformance requirements.
  5. Tests establish only the behavior they execute—never an entire standard.
Important qualification: Jena documents incomplete OWL/Lite reasoning and ShEx limitations. The target must reproduce documented scope, not inflate the reference into full OWL or full ShEx conformance.
